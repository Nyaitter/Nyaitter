# データベースの初期化・更新（マイグレーション）

`server/migrations/` の SQL を順番に適用します。適用済みのファイルは記録され、再実行されません。

> **注意:** リポスト復旧用の `033_fix_repost_content.sql`（PostgreSQL）と `0020_fix_repost_content.sql`（D1）は、2026-11-01 に撤回し、削除しました。本文・添付の一致だけでは、正当な引用ポストと壊れたリポスト行を区別できず、誤って引用を消すおそれがあったためです。既存の壊れた行は、引用ポストとして表示される形で残ります。再発は、repost 作成側の前方修正（本文・添付をコピーしないこと）と、`Server` の `npm test` に含まれる再発防止テスト（`repost.test.js`）で防ぎます。
>
> 適用済みの内容を、ファイルの変更だけで修復することはできません。適用履歴を操作したり、SQL を手動で再実行したりしないでください。

## 実行する

`server/.env` にデータベースを設定し、リポジトリのルートで実行します。

```bash
npm run migrate
```

実行前にデータベースをバックアップしてください。PostgreSQL で特定のファイルだけ適用する場合は `npm run migrate -- --only <ファイル名>` を使います。

PostgreSQL を選択している場合、接続URLが未設定なら runner は失敗（終了コード `1`）し、適用成功とは扱いません。`DATABASE_URL`（または `POSTGRES_URL` / `database.postgres.connectionString`）を設定してください。`--help` はDB接続なしで表示できます。

`DB_ADAPTER=d1` は D1 用の Wrangler migration コマンドへ委譲します。`DB_ADAPTER=memory`（既定値）は永続マイグレーション不要として正常終了します。どちらも PostgreSQL の接続URLは必要ありません。

## データベースごとの設定

| データベース | `server/.env` に書く内容 |
|---|---|
| PostgreSQL | `DB_ADAPTER=postgres`<br>`DATABASE_URL=postgres://...` |
| Cloudflare D1 | `DB_ADAPTER=d1`<br>`D1_WORKER_URL=https://...`<br>`D1_WORKER_TOKEN=...` |

D1 では `workers/d1-proxy` で `npm install` を済ませてください。適用先は既定でリモートです。ローカルの D1 に適用する場合は `D1_MIGRATION_TARGET=local` を設定します。

## データ移行のスナップショット形式

`npm run migrate:data` のスナップショットは現在 `version: 2` です。`tables_present` に「実際に含むテーブル」を列挙します。ここに無いテーブルは、旧形式のスナップショットと同じく**宛先の既存データを保持**します（空で上書きしません）。

`version: 1` の旧スナップショットもそのまま読み込めます。旧形式には「未対応で省略した」のか「対象が0件」なのかを区別する情報が無いため、キーそのものが無いテーブルは省略とみなして保持します。

移行対象外のテーブルは `excluded_tables` に理由付きで記録します。全部で17表あり、内訳は投稿イベントの一時キュー（`post_events`）が1表と、コミュニティノート・レピュテーション系が16表です。ノート本文や評価を含むこれらのデータは移行対象ではありません。

### 置換で消える範囲

スナップショットに `users` または `posts` が含まれる置換では、ノート・レピュテーション系16表のうち13表の既存データが消えます。対象はノート本文・評価・理由・配布・投票記録、作成記録、選定ID、評判イベント・日次集計・プロフィール、審査結果候補・記録です。投稿の削除からノートが外部キーで削除され、ノート削除トリガーが評判イベントを消します。ユーザー削除もユーザーを参照する評判・選定・審査データを外部キーで削除します。投稿削除トリガーも投稿の評判イベントを削除します。結果の `cascaded_tables` に連鎖先が表示されます。

`note_reason_tag_defs`、`reputation_scopes`、`reputation_notice_claims` の3表は、この置換による連鎖削除の対象ではなく残ります。投稿イベントの一時キュー `post_events` は PostgreSQL では残りますが、D1 では投稿投入による過去通知の生成を防ぐため、移行後に必ず空にされます（移行後に再生成可能です）。D1 の `post_events` がまだ作成されていない古い宛先では対象外です。`groups` や `spaces` だけを置換する場合も、ノート・レピュテーション系16表は連鎖削除されません。

消えた13表のデータは置換後に自動復元されず、この移行から再構築もできません。新しい投稿・ユーザーIDとの対応が保証できないため、行を戻すこともしません。残る側は、連鎖削除されない3表と `post_events`（PostgreSQL の場合）を合わせた4表です。理由タグの定義を作り直す必要がある場合は、migration のシードを再実行できます。

### 実行結果に表示される情報

- `counts`: 置換後の件数（含まれないテーブルは `null`）
- `compared_tables`: 件数比較したテーブル数。含まれないテーブルは比較しません
- `preserved_tables`: スナップショットに含めず残したテーブル
- `cascaded_tables`: 連鎖削除されたテーブル
- `cleared_tables`: 連鎖削除とは別に、移行処理で空にしたテーブル（D1 の `post_events` など）
- `skipped_columns`: 宛先DBに列が無くコピーできなかった列（例: D1 に無い `posts.view_content`）
- `excluded_tables`: 移行対象外のテーブルと理由

宛先が InMemory の場合は扱いが異なります。InMemory には外部キーの連鎖削除が無いため、移行対象外のノート・レピュテーション系16表は消えずに保持され、結果の `preserved_tables` と `excluded_tables` の両方に現れます（移行はされないが、宛先の既存データは残る、という意味です）。

カウンタ（`posts.like_count` など）と DM 一覧の集約列（`group_dms.message_count`）は値をコピーせず、移行先の実データから再計算します。D1 はトリガーで加算するため、値の投入と再計算を併用すると二重計上になるためです。

PostgreSQL の置換はデータ更新をトランザクション内で実行します。D1 も 1 回のバッチで実行するため、失敗時は全体が元に戻ります。ただしどちらも置換前にバックアップし、終了後の表示内容を確認してください。

## D1 の制約（既定のまま）

D1 の置換は 1 回の原子的バッチで行います。Cloudflare の上限は 1,000 ステートメントです。移行対象は38テーブルなので、実際に入れられるのは**合計約950行まで**です。超えるスナップショットは削除前に拒否されます。行数を減らすか、バックアップからの再投入で対応してください。
