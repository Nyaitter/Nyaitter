# 本番に出すときのチェックリスト

Nyaitter サーバーを本番環境に載せる前・載せたあとに確認する項目です。

## 1. デプロイ前に必ず確認すること

### データベース

- [ ] `DB_ADAPTER=postgres` になっている
- [ ] `DATABASE_URL` が正しく、接続できる
- [ ] 本番用のデータベースにスキーマが入っている
- [ ] 接続プールのサイズが妥当（目安：CPU コア数の 2〜4 倍）
- [ ] SSL 接続が有効（`sslmode=require` など）

### ストレージ

- [ ] `STORAGE_ADAPTER=r2`（または本番向けのストレージ）になっている
- [ ] R2 の認証情報（Access Key / Secret）が正しい
- [ ] 公開用ドメインが設定され、ファイルにアクセスできる

### セキュリティ

- [ ] `NODE_ENV=production`
- [ ] `DEV_BYPASS_AUTH` が false か未設定（本番で true にしない）
- [ ] リバースプロキシの後ろで動かす場合は `TRUST_PROXY=true`
- [ ] HSTS を本番で有効にするか検討した
- [ ] Turnstile のシークレットキーが正しい

### ログと監視

- [ ] `LOG_LEVEL` が適切（本番は `info` 以上を推奨）
- [ ] エラーログがどこかに集まる仕組みがある

## 2. できるだけやっておくこと

- [ ] 終了信号（SIGTERM）を受けたときの終了処理が動くことを確認した
- [ ] 監視ツールから次を叩ける
  - `/server/health`
  - `/server/ready`
- [ ] レート制限が有効（特に `/server/auth/*`）
- [ ] バックアップの方針が決まっている（DB のダンプ、R2 の版管理など）

## 3. Cloudflare を使う場合の追加確認

### D1 を使うとき

- [ ] D1 用の Worker がデプロイ済み
- [ ] Worker の認証トークンが Node 側に正しく渡されている
- [ ] Worker 側で許可する操作が、あらかじめ決めたものだけになっている

### R2 を使うとき

- [ ] バケットの CORS 設定が済んでいる（ブラウザから直接上げる場合）
- [ ] 公開ドメインが正しい
- [ ] 署名付き URL 用の Worker を使う場合、その認証が効いている

## 4. デプロイ後の確認

- [ ] サーバーが起動し、ログにエラーが出ていない
- [ ] `/server/health` が 200 を返す
- [ ] `/server/ready` が 200 を返す
- [ ] ログイン → 投稿 → ファイルアップロードの一連の流れが動く
- [ ] ログにリクエスト ID（`x-request-id`）が出ている
- [ ] 短時間に大量リクエストを送ると 429 が返る（レート制限の確認）

## 5. 本番でやってはいけないこと

- `DEV_BYPASS_AUTH=true` を設定する
- InMemoryAdapter を本番で使う
- ローカルストレージを本番のメイン保存先にする（できれば避ける）
- パスワードやキーをコードに直書きする
- 弱いデフォルトの `AUTH_TOKEN`（D1 Worker 用など）をそのまま使い続ける
